## 1) CONTRIBUTING.md template (drop-in)

````md
# Contributing

This repo follows a **develop + main** workflow with **CI-first discipline**:
- `develop` is the integration branch (always green).
- `main` is production (always deployable).
- Work happens on short-lived branches and lands via PR + CI.

---

## Branching Strategy

### Long-lived branches
- **`main`**: Production-ready code. Only updated via release PRs and hotfixes.
- **`develop`**: Integration branch for all completed work. Must stay green.

### Short-lived branches
Create branches from `develop`:

- **`feature/<ticket>-<short-name>`**  
  Example: `feature/CLIK-142-auth-navigation`
- **`fix/<ticket>-<short-name>`**  
  Example: `fix/CLIK-201-crash-on-start`
- **`chore/<short-name>`**  
  Example: `chore/update-deps`

### Hotfix branches
For urgent production issues:
- **`hotfix/<ticket>-<short-name>`** branched from `main`
- Merged back into `main` (deploy), then also merged into `develop`

---

## Development Workflow

### 1) Sync `develop`
```bash
git checkout develop
git pull origin develop
````

### 2) Create a branch

```bash
git checkout -b feature/<ticket>-<short-name>
```

### 3) Commit using Conventional Commits

We enforce commit format locally and in CI.

Example:

```bash
git add .
git commit -m "feat(auth): add login route guard"
```

### 4) Push & open a Pull Request

```bash
git push -u origin feature/<ticket>-<short-name>
```

### 5) PR rules

A PR can merge only when:

* ✅ CI checks pass (lint, tests, build)
* ✅ At least 1 approval (or team-defined)
* ✅ No unresolved review comments
* ✅ PR title follows Conventional Commits
* ✅ Branch is up to date with `develop`

### 6) Merge method

* **Squash merge** only (keeps history clean)
* Delete branch after merge

---

## Release Workflow (every sprint)

At the end of each sprint:

1. Open PR: `develop → main`
2. Ensure CI is green
3. Merge and deploy (via CI/CD)
4. Tag a release (if your pipeline uses tags/releases)

---

## Hotfix Workflow (production issues)

1. Branch from `main`:

```bash
git checkout main
git pull origin main
git checkout -b hotfix/<ticket>-<short-name>
```

2. Fix + commit + PR into `main`, deploy
3. Merge `main → develop` (or cherry-pick) so develop stays current

---

## Commit Message Convention (Conventional Commits)

Format:

```
type(scope): description
```

Allowed types:

* `feat`, `fix`, `docs`, `style`, `refactor`, `test`, `chore`, `perf`, `ci`, `build`, `revert`

Examples:

* `feat(auth): add JWT token validation`
* `fix(ui): resolve mobile layout overflow`
* `ci: add commitlint workflow`

---

## Local Quality Checks

Run before pushing:

* `pnpm lint`
* `pnpm test`
* `pnpm typecheck` (if available)
* `pnpm build` (recommended)

````

## Scene 2 (1:10–2:10) Create branch properly
**On screen:** Terminal commands.

```bash

git checkout -b feature/CLIK-142-auth-navigation
````

**Say:**

> “Always sync `develop` first, then branch from it. Keep branches small and short-lived. If your branch lives for a week with 50 commits, it’s not a feature branch, it’s a future incident report.”

## Scene 3 (2:10–3:20) Conventional commits + enforcement (the memorable part)

**On screen:** Make a small code change.

### Part A: show a **bad commit** getting blocked

**Show:**

```bash

```

**Expected result:** commit-msg hook fails (or CI would fail later if hooks aren’t installed).

**Say:**

> “We enforce Conventional Commits. Random messages like this get blocked because they break changelogs, release notes, and debugging. Use a real type and optional scope.”

### Part B: show the correct commit

**Show:**

```bash
git commit -am "feat(auth): add route guard for logged-out users"
```

**Say:**

> “This format also makes PR history readable and makes releases cleaner.”

*(If you use Commitizen, show `pnpm cz` or `npm run commit` instead.)*

**On screen:** Push branch; open PR in GitHub.

**Say:**

**On screen:** CI checks running/passing.

## Scene 5 (4:40–5:40) Review + squash merge

**On screen:** PR review screen.

**On screen:** Bullet list slide (or README section).

## 3) Enforcing “no random commit types / branch names” (practical setup)

You said you already do this, so here’s the standard stack that works and doesn’t become a science project:

### Local enforcement (dev machine)

* **Husky** + **commitlint** → blocks bad commit messages
* **lint-staged** → runs formatter/lint on changed files only

### Remote enforcement (can’t be bypassed)

* GitHub Action that runs **commitlint on PR commits**
* GitHub Action that validates **branch naming**
* Branch protection requires those checks
